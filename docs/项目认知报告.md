关键结构性事实（`packages/*/package.json` 与 tsconfig 实测）：

- **`durable` 不复用 `agent`。** 它依赖 `chord, ai, diff, typebox`，自带 `src/harness/*`（自有 agent 循环、compaction、scheduler、inbox、task-graph）与 `src/tools/{read,write,edit,bash}.ts`（自研工具）。它也不依赖 `tui` 与 `coding-agent`。
- **`coding-agent` 不依赖 `durable`。** 两条栈并列：`durable` 建在 `chord` + `ai` 上，`coding-agent` 建在 `chord` + `agent` + `ai` + `codemode` + `mcp` + `tui` 上，由 `coding-agent` 承担唯一的顶层组装。
- durable 的可运行示例以**未发布应用**形式内嵌在 `packages/coding-agent/src/experimental/durable/`（`harness-setup.ts`、`main.ts`、`runtime.ts`、`sessions.ts`、`subagent.ts`、`tui.ts`）。`packages/coding-agent/tsconfig.build.json` 的 `exclude` 含 `src/client`、`src/experimental`、`src/cli/experimental`，因此这段代码**被根 `tsconfig.json` 类型检查，但不进 `dist`、不进 npm 包**；它对 `pi-durable` 的引用靠根 tsconfig 的 `paths` 与 `src/experimental/source-resolver.ts` 在源码模式成立，属于「仅源码模式可用」。
- `durable/README.md` 首行自标 **Experimental**，明确「API changes without notice between releases」。
- `packages/apps/` 只有空的 `web/`、`desktop/` 两个目录，**无 package.json**——与《开发规范》第 40 行「不建立占位 package.json」一致。
- `packages/session-backends/` 只剩一个 vitest 缓存残留，未被 Git 跟踪，属历史遗留。

依赖方向分三层：基础层（chord / tui / telemetry / codemode / mcp）→ 模型与运行时层（ai → agent → coding-agent）→ **并列的 durable 栈**。

这条结构对二开方案有三点直接含义：

1. 「durable 优先 + coding-agent 兼容」双执行器是**两个独立栈**，不是一个栈的两种模式——这正是不共同写入同一运行时存储的技术依据，也说明 `cyg-runtime` 的适配层不是薄封装。
2. durable 目前只服务未发布的 experimental 代码，**不进任何构建产物**。要把它作为平台执行器，必须先解决「如何正式接入依赖与构建」这个问题，而不是直接 import。
3. 平台若同时依赖两个栈，`cyg-runtime` 必须显式声明 `pi-durable`，不能沿用 experimental 那种「靠 tsconfig paths 绕过声明」的做法。

### 4.2 原型的真实运行形态（源码可证实）

- 启动链：`启动 Pi Web.vbs` → `start.ps1` → `node --import packages/coding-agent/src/experimental/source-resolver.ts live-main.ts --cwd <repo>`。启动前校验 Node、`node_modules`、模型数据与源码哈希；宿主存活且版本一致则复用，版本不符只提示、不杀进程。

- 真实执行层只有 `host-runtime.ts`：通过 `createAgentSessionRuntime` / `createAgentSessionServices` 建会话，切会话走 `replaceRuntime`，事件走 `subscribe`。宿主命令分三个 surface：`rpc` / `sdk` / `host`，其中 `web.*` 是**宿主路由，不是 Pi 官方 RPC**——这是文档反复强调的关键区分。
- 桥接三路由（`host-http.mjs`）：`POST /bridge/bootstrap` 签发 HttpOnly + SameSite=Strict cookie 与 CSRF；`POST /bridge/dispatch` 需 cookie + `X-Pi-Web-Token` 双校验；`GET /bridge/events` 为 SSE，接入即分配终端所有者并推初始状态，含心跳与租约回收。
- 本机保护落点（`host-http.mjs`）：Host 白名单、Origin 必须等于 Host、拒绝 `Sec-Fetch-Site: cross-site`、安全响应头、静态文件 realpath 前缀校验。宿主仅绑 `127.0.0.1`。
- 离线演示与真实模式分离：`engine.js` 头部自述为离线 UI 模拟器，不是 Pi 传输层。

### 6.1 阻塞点：doc-html 生成器与 TypeScript 7.0.2 不兼容

根因链（实测）：

1. 仓库声明 `typescript@7.0.2`（根 `package.json`）。
2. TS 7.0.2 的包主入口 `.` 只指向 `lib/version.cjs`，实测 `Object.keys(require('typescript'))` 仅 `['version','versionMajorMinor']`。
3. `docs/doc-html/src/catalog.mjs:1` 使用 `import ts from 'typescript'` 并调用 `ts.createSourceFile(..., ts.ScriptTarget.Latest, ...)`，于是 `parseSource` 抛 `TypeError: Cannot read properties of undefined (reading 'Latest')`。
4. 直接后果：catalog 相关 4 项测试失败 + `buildCatalog` 无法运行 → 生成数据停在旧提交；另 4 项失败是陈旧快照断言（生成数据记录 `229d6fd`，HEAD 为 `517e9fd`）。

补充实测：TS 7 的新 API 子路径 `typescript/unstable/ast`、`/unstable/ast/is`、`/unstable/sync` **是可用的**，两个根检查脚本正是用这套 API，因此正常通过。也就是说：坏的只有仍使用旧版 Compiler API 的 doc-html 生成器，不是全部 TS 工具链。

修复方向二选一：把 `catalog.mjs` 迁到 `unstable/ast`（工作量取决于 AST 遍历、注释区间、行号等用法），或让 doc-html 使用独立的 TS 5.x 解析依赖。方案需按《开发规范》第 58 行评估依赖升级，而不是为消错删功能。

## 7. 在飞改动：Pi 核心两处（已实测通过回归）

工作区对 Pi 核心只有两处改动，均未提交。

**1. `packages/coding-agent/src/core/agent-session.ts:3621`**
在设置重载路径（`settingsManager.reload()` 之后）补上 `this._cacheWarmer?.onModeChanged();`。
问题：通过设置选择器改缓存预热模式时，`setCacheWarmingMode()`（同文件 1406-1409）已会调用 `onModeChanged()`，但设置从磁盘重载的路径漏了这一调用，导致预热策略与刚重载的配置不一致，已激活的预热不会按新配置收敛。
`cache-warmer.ts:260` 的 `onModeChanged()` 语义就是「按持久化模式重新校正正在运行的预热」。
实测：`test/cache-warmer.test.ts` 9/9 通过。

**2. `packages/coding-agent/src/modes/interactive/external-editor.ts:26-31`**
Windows 改为把整条命令拼成单个字符串交给 `shell: true`。
问题：原实现 `spawn(editor, [...editorArgs, filePath], { shell: true })` 在 Windows 下由 Node 自行拼接参数且**不加引号**；临时提示文件路径含空格时会被拆成多个参数，编辑器打开错误文件或失败。
修复后单个命令行内显式加引号，并保留原注释所述「不能用 `spawnSync`」的原因（Windows 上同步子进程会与 vim/nvim 争抢控制台输入缓冲）。
实测：`test/external-editor.test.ts` 3/3 通过；该测试的编辑器命令本身含空格（Node 安装路径），覆盖了此回归。

残留观察（非结论）：该改动把 Windows 分支的实际执行者从「Node 直接 spawn」变成「cmd.exe 解释整条命令串」，因此编辑器命令中如含 shell 元字符会被 cmd 解释；非 Windows 分支仍不支持含空格的编辑器路径（既有局限，本次未修）。两个分支共享的 `options.command.split(" ")`（`:19`）在 Windows 下已不再用于构造 argv，仅非 Windows 分支使用。
