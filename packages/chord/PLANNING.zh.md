# Chord实现计划

> **状态**：活动实现计划。上下文、严格JSON、复制状态、服务发布/消费、facet主机/加载器，以及初始Node facet捆绑和生成加载现已在Chord中实现。对称RPC和结构生成替换仍为计划内容。这还不是稳定的公共API契约。

## 1. 目标

Chord将作为应用无关的基础，用于：

1. 加载、组合、卸载、重新加载和捆绑插件；
2. 声明和消费本地或远程服务；
3. 通过对称RPC管道传输服务调用和订阅；以及
4. 将权威的最新值状态复制到本地和远程消费者。

当前Pi实验已验证许多所需行为，但Chord将从头实现。现有源码可作为测试和设计依据，不会被复制到本包中。与实验API或线协议的兼容性不是要求。

## 2. 依赖边界

依赖方向严格：

```text
@earendil-works/chord
        ↑
Pi agent, protocol, server, coding agent, TUI, and future applications
```

Chord必须：

- 不依赖于另一个Pi工作区包；
- 不导入`@earendil-works/pi-*`或`packages/chord`之外的相对路径；
- 源码、错误、测试和示例使用应用无关词汇；
- 拥有其公共API所需的任何通用运行时类型，包括严格JSON值和调用取消上下文；
- 将Node特定的加载和捆绑与平台无关的运行时分开；
- 可独立构建、测试、打包和使用，无需解析另一个Pi包。

通用第三方依赖不禁止，但每个依赖必须有据可依。运行时应优先使用标准JavaScript API。打包器可使用一个由Chord拥有的适配器封装的固定实现。

以下术语不得成为Chord概念：Session、Harness、AgentLane、server、client、attachment、TUI、model、tool、hook、provider credential或workspace。这些属于消费者。

## 3. 架构模型

### 3.1 工作词汇

以下名称暂定，但区分是必需的。

- **插件**：一个独立激活的组合单元，具有稳定ID和同步设置函数。
- **插件模块**：一个导出一个或多个插件的JavaScript模块，供应用选择入口。
- **加载生成**：插件及其加载模块生成所拥有的资源。
- **主机**：一个组装的插件和服务图。
- **服务令牌**：一个稳定的运行时服务ID，加上类型信息和本地性策略。
- **提供者**：一个单一实例服务或键控服务集合的所有者。
- **连接**：一个传输无关的服务源，位于当前主机之外。
- **对等节点**：对称RPC通道的一个端点。任一端点均可提供和消费服务。
- **复制状态**：已初始化的不可变源修订版，具有只读本地或远程副本。

一个产品功能可能为不同应用环境提供多个插件模块入口。Chord不会将这些入口组合成跨进程运行时对象，也不会解释其入口名称。

### 3.2 分层

实现应分为以下层：

```text
plugin loader and bundler
        ↓
plugin host, lifecycle, and dependency graph
        ↓
service tokens, providers, facades, and keyed instances
        ↓
replicated state and service subscriptions
        ↓
symmetric RPC peer and transport adapter
        ↓
strict JSON, invocation context, cancellation, and errors
```

本地服务路径不得要求RPC序列化。远程路径必须通过严格线边界使用相同的服务语义。

## 4. 调用上下文和严格JSON

当前实验依赖于Pi的Harness `Context`，Chord无法导入。Chord因此需要一个小型中立调用上下文。

初始上下文应提供：

- 一个可选`AbortSignal`，用于取消一个调用或观察；
- 通过Chord拥有的上下文键提供的不可变类型本地值；
- 一个背景根；
- 子项派生、取消和取消感知的等待辅助函数；以及
- 无内置遥测、身份、认证或应用值。
应用程序可以定义自己的上下文密钥。Pi适配器可以通过这些密钥携带遥测数据和已认证的身份信息，而无需Chord知道它们的类型。

上下文对象作为业务值永远不会通过RPC传递。调用方会发送取消控制信号，如果配置了，则还会携带一个不透明的严格JSON元数据载体。接收方适配器会构造一个新的本地上下文。适配器，而不是远程业务参数，负责安装已认证的本地身份。

Chord拥有静态`JsonValue`合约，并为适配器边界提供`JsonRepresentation<T>`和`isJsonValue()`。服务运行时故意不执行自动递归验证；具体序列化器仍需负责拒绝不支持的值。远程参数、结果、错误、快照、更新、目录和RPC信封都应是有限的严格JSON：

- 仅限有限数字；
- 不允许`undefined`、稀疏数组、符号、原型、循环、类、函数、`Map`或`Set`；以及
- `null`，而非`undefined`，表示业务层面的缺失。

应用程序模式验证仍由应用程序负责。Chord验证结构控制信封，但严格JSON边界的运行时强制执行目前推迟到序列化器。

## 5. 插件和生命周期

### 5.1 插件形状

预期的作者模型等同于：

```ts
interface Plugin {
  readonly id: string;
  setup(environment: PluginEnvironment): void;
}
```

安装是同步声明。它可能：

- 提供单例服务；
- 声明对键控服务的所有权；
- 获取单例服务句柄；
- 声明对键控服务实例的观察；
- 创建复制状态；
- 注册激活回调；
- 注册已拥有资源的清理；以及
- 注册最终去激活工作。

安装不得：

- 通过已获取的外观调用服务或读取复制状态；
- 执行异步工作；
- 从事件处理器或激活回调引入新的服务依赖；或
- 修改活动主机生成。
主机记录设置调用在一个私有的生成账本中。插件作者不需要维护并行的`requires`/`provides`清单。

### 5.2 组装

在每个插件完成设置后，主机必须：

1. 收集本地配置和从已配置的远程服务源获取的目录；
2. 将每个硬性需求解析为一个本地或连接的提供者；
3. 拒绝缺失的提供者、重复的提供者、模糊的源提供以及单例/键值不匹配；
4. 拒绝重复的插件ID；
5. 推导提供者到消费者生命周期边；
6. 拒绝依赖循环；
7. 在句柄仍不可用时构建本地和远程服务绑定；
8. 填充所需的连接服务；以及
9. 在消费者之前激活提供者。

插件可以提供和消费相同的令牌而不创建自循环。可选依赖关系不属于第一个契约；它们需要在稍后通过独立的获取API获取。

### 5.3 资源所有权

每个插件生成拥有：

- 激活回调；
- 显式的清理函数；
- 通过其提供者句柄添加的键值实例；
- 键值观察及其任务；以及
- 服务提供。

处置是幂等的。消费者在提供者之前停用，每个插件的资源按反向注册顺序释放。清理会在单个失败后继续，并在所有清理尝试完成后报告一个错误或`AggregateError`。

键值观察处理器会收到一个全新的可取消上下文。关闭或替换实例只会中止该处理器任务。处理器失败会通过主机策略报告，除非其上下文被正常清理。

### 5.4 已加载的模块生成

模块加载和插件激活是独立的所有权域：

```ts
interface LoadedPlugins {
  readonly plugins: readonly Plugin[];
  dispose(): Promise<void>;
}

interface PluginLoader {
  load(): Promise<LoadedPlugins>;
}
```

必需的加载器：

- 一个用于内置和测试的静态加载器；
- 一个有序组合加载器，具有反向释放和启动失败清理；以及
- 一个用于加载单个选定清单条目的捆绑/模块加载器。

加载器拥有一个源生成版本。主机拥有活动插件生命周期。协调器必须在丢弃其`LoadedPlugins`之前，先停用已退休的生成版本。

Node的默认ESM加载器会将其进程范围缓存中保留每个导入模块的生成版本。Chord因此将Node面元打包为CommonJS，并直接使用`node:vm`编译每个生成版本，而不向Node模块缓存中插入插件代码。Chord的卸载契约仍然是停用、移除服务可达性、清理和释放加载器拥有的引用/资源。一旦没有插件创建的定时器、监听器、回调或其他已逃逸的引用剩余，V8就可以垃圾回收已编译的生成版本；回收时机不是确定性的。

## 6. 加载、卸载和重载

### 6.1 主机更新

主机更新是序列化的，并且有两种形式。

#### 形状保持替换

当每个被替换的插件都保持相同的：

- 插件ID；
- 所需的服务ID和模式；
- 提供的服务ID和模式；以及
- 可远程暴露的单例成员名称和类型。

顺序如下：

```text
load replacement module generation
→ run replacement setup
→ validate replacement shape and remote implementations
→ activate replacements in dependency order while the old providers remain routed
→ replace each local or remote singleton directly without withdrawing it
→ deactivate replaced plugins in reverse dependency order
→ dispose the retired loaded generation
```


属性：

- 现有的本地和远程单例面元保持对象身份；
- 捕获的本地和远程方法在切换前会转发到旧提供者，在切换后转发到替换提供者；
- 复制状态的面元在不脱水的情况下安装替换快照；
- 每个单例会直接从其旧目标切换到其替换版本，但多服务重载不是图事务；
- 来自旧插件的关键实例关闭；由替换版本暂存的实例使用新的生成版本；
- 设置、形状验证或替换激活失败会保持当前活动生成版本不变；
- 在激活期间获取的命名主机资源支持重叠暂存替换，因此候选清理会恢复旧注册，而退休清理无法移除替换版本；以及
- 任何在替换开始后的失败会终止主机，而不是尝试保持部分转换的图。

切换后没有回滚。最终清理会在尽力范围内撤销每个面元句柄；只有切换前的候选清理和普通的主机丢弃能保证依赖顺序的清理。已提交的应用效果在重载事务之外。

#### 结构替换

添加或移除插件、更改服务形状或更改连接选择属于结构变更。第一个实现应替换完整的主机生成版本，而不是尝试部分受影响子图的更新：

```text
load and synchronously set up the complete desired generation
→ resolve and validate its graph without activation effects
→ begin cutover
→ withdraw old providers and deactivate the old graph
→ install and activate the new graph
→ dispose the old loaded generation
```


规则：

- 切换前的验证失败会保持旧图活跃；
- 切换开始后，失败会丢弃整个主机，因为退休的图无法恢复；
- 在候选验证期间，移除提供者同时保留硬消费者会被拒绝；
- 当服务ID和模式在替换中得以保留时，插件生命周期外拥有的服务面元保持稳定；
- 被移除的服务对退休生成版本永久断开连接；以及
- 未来优化可能会保留未受影响的插件，但这不是初始结构更新的必需。

这条完整的生成路径提供了实际插件加载和卸载语义，而无需先实现复杂的部分图事务。

### 6.2 卸载期间的调用

替换永远不会让单例面元失去目标：调用会解析旧实现或其替换版本。在退休面元中已运行的工作不会被清空；之后使用该面元撤销的句柄可能会因过期工作而失败。未来的可杀死隔离主机会直接终止此类工作。传输断开仍然只会取消连接拥有的调用，不会隐含应用级取消或回滚。

### 6.3 更新失败报告

更新结果必须区分：

- 加载失败；
- 切换前的设置或图验证失败；
- 旧生成版本停用失败；
- 替换激活失败；
- 服务重新绑定失败；以及
- 已退役加载器处置失败。

多个失败被聚合，且不会隐藏首次转换失败。并发的更新、卸载和主机处置请求会被序列化或拒绝，并返回一个稳定的生命周期错误。

## 7. 服务

### 7.1 令牌和模式

服务令牌具有：

- 一个非空的稳定字符串ID；
- 一个 TypeScript 合约类型；
- 一个本地性策略：默认为远程可暴露，或显式为进程本地；以及
- 没有自己的提供者实例。

Chord 为控制面ID保留前缀。同一目录中的重复ID无效。

需要两种模式：

- **单例**：一个提供者，多个消费者；以及
- **键控**：一个集合所有者，动态实例，多个观察者。

一个令牌在一个主机图中只能有一种模式。混合使用单例和键控模式是组装或协议错误。

### 7.2 本地服务

进程本地服务：

- 可以暴露任意对象、同步方法、类、函数、原生句柄或非JSON值；
- 永远不会包含在远程目录中；
- 使用与远程服务相同的图排序、稳定句柄、键控生成和生命周期行为；以及
- 受信任的组合，不是安全边界。

本地单例消费者会收到一个稳定的懒加载外观，而不是提供者对象。这消除了设置顺序依赖，并允许提供者替换更新捕获的方法。

远程可暴露的服务在提供者和消费者共享主机时也会使用提供者/绑定路径。内部环回绑定保持替换、复制状态和键控生成语义与放置无关。只有显式进程本地服务才会绕过该路径。

### 7.3 远程服务合约

远程可暴露的实现中，只有自己的数据属性可以被分类为：

- 异步方法，其业务参数和结果为严格的JSON，且在声明位置只有一个Chord调用上下文；或者
- 品牌复制状态值。

提供者会从实现中派生运行时成员表。插件作者不需要维护第二个方法/状态描述符。不支持的访问器、字段或成员类型在发布前会被拒绝。

类型级别的检查应该拒绝明显无效的远程合约。运行时检查仍然必要，因为类型无法验证对等方或在JavaScript消费中存活。

远程方法：

- 返回承诺；
- 返回严格的JSON或`void`；
- 接收一个新鲜的本地调用上下文；
- 将调用者取消映射到恰好一个请求；
- 断开连接时不排队；以及
- 暴露稳定的错误代码和净化后的消息。

任意返回对象引用、回调、函数序列化和一般对象图远程调用超出了初始范围。

### 7.4 稳定单例外观

`use(token)`返回一个由facet拥有的能力视图，覆盖一个与源无关的主机服务槽。在同一个facet内重复获取会返回相同的视图；不同facet生命周期会收到不同的视图。成员槽在属性访问时懒加载，并在绑定时根据提供者元数据进行验证。

必需的行为：

- 在设置期间和facet生命周期结束后不可访问；
- 在本地图组装或远程水合后直接绑定；
- 跨提供者撤回和替换时保持稳定；
- 断开连接时方法调用失败；
- 未水合时状态读取返回`undefined`；
- 远程可暴露的替换保留完整的成员名称/类型表；以及
- 提供者省略已访问成员是一个绑定错误。

### 7.5 键控服务

`provideMany(token)`在设置时声明一个键控所有者，并返回一个由generation拥有的`ServiceSpawner`。在活动期间，`spawn(key, implementation)`：

- 需要一个非空且在所有实例中唯一的键；
- 为该键创建一个由主机拥有的单调递增生成；
- 原子地发布方法和初始状态；
- 返回一个幂等关闭函数；  
- 在插件清理时会自动关闭。

实例地址为`(service ID, key, generation)`。复用已关闭的键会创建新生成。过期的外观无法调用替换。

`observe(token, handler)`：

- 负责完成初始实例目录的协调；  
- 仅在所有初始状态成员完成加载后，才为每个实例启动一个任务；  
- 保持有序的添加、替换和移除；  
- 在关闭、替换、断开连接或观察清理时，会中止实例任务；  
- 为每个观察提供一个观察生命周期的服务视图，该视图在任务中止后变得不可访问；以及  
- 永远不会在复制的JSON状态中表示服务外观。

## 8. 复制状态

复制状态是权威的单写最新值复制。

源API有一个已初始化的不可变值，`change(context, callback)`，`replace(context, value)`，以及订阅功能。远程或断开连接的副本在加载前有`value === undefined`。

必需语义：

1. 源始终已初始化。  
2. 源和副本的值必须是严格的JSON，用于远程暴露的状态。  
3. 订阅已初始化的本地或加载的副本状态会立即获得当前值，并带有新鲜的交付上下文。  
4. 订阅冷状态时不会立即交付。  
5. 订阅建立时会先捕获更新，再取快照。  
6. 与快照竞争的更新会被缓冲，并在快照之后无间隙地交付。  
7. 源API暴露原子级Copy-on-Write事务。成功事务发布一个解码的操作批次；回调失败则丢弃所有暂存副本。连接适配器为每个客户端/状态流独立编码每个批次，副本仅按顺序应用批次。  
8. 序列间隙会清除就绪状态并触发完全重新订阅，或报告终端绑定错误；过期状态必须静默终止，不能继续作为当前状态。  
9. 断开连接、提供者退出、路由变更和替换会清除副本就绪状态。  
10. 重新连接或替换会在现有状态外观中安装一个完整的全新快照，之后再应用更新。  
11. 监听器异常会被隔离并通过主机策略报告。  
12. 值是不可变数据。Chord返回原始不可变值用于读取和监听交付。事务草稿可撤销，分配的容器按值复制；提交的修订共享未变更的子树。

状态身份是结构性的：

```text
provider binding + service ID + optional keyed address + member name
```
  
没有独立的状态ID。

显式非目标：

- 持久性或进程重启后的重建；  
- 事件历史；  
- CRDT合并或多写；  
- 离线突变回放；  
- 高频流传输。

Chord暴露一个保持意图的JSON delta原语，并使用其操作批次处理远程复制状态。初始加载和重新连接会携带完整的根替换。生产者在一个事务范围内对复制写草稿；Chord从前后不可变修订推导紧凑操作，当完整替换更小时则使用。复制状态源不会选择归约器或与路径编码器交互。每个客户端/状态配对拥有独立编码器，序列处理会在后续操作应用前拒绝间隙。

## 9. 对称RPC管道

### 9.1 无客户端/服务器模式

Chord不得暴露`Client`，`Server`，`SessionConnection`或类似拓扑类。它通过应用提供的双工通道暴露对称对等节点。任一端点均可注册处理器、提供服务、调用方法或订阅状态。

应用适配器拥有：

- 套接字、管道、WebSocket、工作线程或回环交付；  
- 帧构造和重连策略；  
- 认证和授权；  
- 路由和目标选择；  
- 进程所有权；  
- 附加或选择状态；以及  
- 围绕Chord消息的应用协议信封。
弦连接到一个对等节点，并且已经解码了严格的JSON消息。

### 9.2 RPC层

通用的RPC对等节点应该拥有：

- 对单个对等连接请求ID的分配；
- 请求/响应关联；
- 处理器注册；
- 取消帧和单个请求本地的`AbortController`；
- 断开连接拒绝和清理；
- 稳定的可序列化错误信封；
- 有序的通知交付；
- 对格式错误消息的拒绝；以及
- 可选的上下文元数据钩子。

通道合约应该很小：发送一个严格的JSON消息，按顺序接收消息，观察关闭，并关闭。`send()`应该可等待，以便适配器可以提供背压。

对等节点断开连接：

- 拒绝外出请求；
- 中止入站请求上下文；
- 关闭服务订阅和键控观察任务；以及
- 不取消应用程序拥有的作业或执行持久业务变异。

### 9.3 通过RPC的服务协议
服务层为以下内容增加了与传输无关的操作：

- 目录发现；
- 单例和带键订阅的打开/关闭；
- 完整的订阅快照；
- 方法调用；
- 调用取消；
- 复制状态更新；
- 单例不可用/被替换事件；以及
- 带键实例生成/关闭事件。

线协议中不包含服务器ID、会话ID、附加ID、路由、用户身份或主机类型。Pi路由器可以使用其自己的控制字段封装或转发Chord信封，而不解析服务业务负载。

目录和订阅状态必须来自实际的服务提供，而不是手写的库存清单。

### 9.4 线错误和验证

Chord需要稳定的通用错误代码，例如：

- 服务不允许或不存在；
- 模式不匹配；
- 成员不存在或使用了错误的类型；
- 带键实例不存在或已过期；
- 无效的严格JSON值；
- 取消；
- RPC 消息格式错误；
- 对等方断开连接；以及
- 内部提供方故障。

意外的提供方异常默认被处理为已净化的内部错误。堆栈跟踪和任意异常字段不会跨网络传输。应用程序可以通过适配器注册或映射额外的稳定错误代码，但 Chord 不拥有应用程序错误分类体系。

### 9.5 协议演进

第一个实现必须独立于任何应用程序协议对 Chord 的 RPC/服务信封进行版本化。版本协商可以是节点握手或适配器保证的构造函数参数，但不兼容的对等方必须在服务调用被允许之前失败。

插件生成差异导致的成员和 DTO 兼容性是应用程序的责任。Chord 仅保证其通用信封语义。

## 10. 打包

### 10.1 目的

打包器将一个或多个由应用程序声明的 ESM 或 TypeScript 插件入口转换为独立可加载的 Node CommonJS 资源。它不是包管理器或插件注册表。

每个入口独立构建。Chord 不假设 `server`、`session`、`tui` 或 `web` 这类名称；入口名称是应用数据。

### 10.2 初始输入和输出

打包器初始应接受：

- 插件标识和可选版本元数据；
- 将不透明入口名称映射到 TypeScript 或 JavaScript 源文件的映射；
- 输出目录；
- 由应用程序提供的外部模块白名单；
- source-map 和压缩选项；以及
- Node CommonJS 构建所需的可选定义/平台设置。

包级 API 还接受插件包目录，从 `package.json` 派生标识和版本，应用提供的约定入口路径（如果文件存在），并允许 `chord.facets` 覆盖或禁用约定。包发现不会安装依赖或运行生命周期脚本。

它应输出：

- 每个入口对应一个内容寻址的 CommonJS 文件；
- 源映射（启用时）；
- 版本化的严格JSON清单；
- 内容哈希或完整性值；
- 声明的外部导入；以及
- 足够的元数据以供诊断和新生成加载使用。

写入操作应使用临时输出目录，然后进行原子重命名，以确保加载器不会看到半写入的生成。

### 10.3 打包规则

- `@earendil-works/chord`必须外部化，以便插件使用主机的运行时和品牌符号。
- 其他依赖项默认打包。显式打包API使用应用程序外部允许列表；包级API也会外部化同伴依赖项，因为主机提供了这些依赖项。
- Node入口点可能允许使用内置模块，但这不是信任或沙箱策略。
- 动态导入必须通过加载器的受限`require`降低，未解析的外部符号必须确定性报告。
- 打包输出不得依赖Pi仓库路径别名。
- 重新构建未更改的输入应产生稳定的内容，除非是已记录的元数据。
- 诊断必须标识入口和原始源位置。

具体的打包引擎是实现细节。选择它时，应覆盖TypeScript和ESM输入、CommonJS输出、源映射、外部符号、内容哈希和程序化诊断，然后再添加依赖项。

### 10.4 打包加载

打包加载器必须：

1. 解析和验证清单；
2. 选择一个应用程序请求的入口；
3. 完整性存在时，在激活前验证完整性；
4. 直接使用`node:vm`作为新生成，独立于Node模块缓存编译；
5. 验证其导出项是否为具有唯一非空ID的插件；
6. 返回`LoadedPlugins`；
7. 提供幂等加载器处置。

插件发现、安装、版本解析、下载、签名信任和更新策略仍为应用责任。

| `packages/protocol/src/protocol.ts`通用服务部分 | Chord拥有的版本化服务/RPC信封 |

| `packages/coding-agent/src/experimental/services/server.ts` | 服务器级会话目录和管理实现 |

| `packages/server`、`packages/client`和进程管理器 | 框架、路由、认证、附加、进程生命周期、重连策略 |
| 命令行、模型、账户、对话、TUI和代理控制器服务 | 应用合约和插件实现 |
| `source-resolver.ts`和Pi内部进程入口点 | Pi源执行和进程策略 |

Pico5 Chord使用指南、实验性服务测试和远程插件固定件是行为输入。它们不是规范的Chord API。迁移完成后，通用语义应记录在Chord和Pi文档中，仅覆盖其主机特定的合约和适配器。

迁移应在Chord通过其独立符合套件后进行：

1. 实现Chord而不更改Pi调用者；
2. 添加薄Pi适配器并迁移通用服务导入；
3. 迁移实验性插件主机和加载器；
4. 适配Pi的路由协议以承载Chord信封；
5. 运行本地、回环、带帧、带密钥生成、重新加载和TUI集成测试；

6. 仅在所有消费者都使用Chord后，才删除重复的实验性泛型实现。

除非另行请求，否则不需要兼容性适配层。

- 通用贡献注册表；应用可将其作为进程本地服务暴露；  
- 不确定断开连接后变异调用的自动重试；以及  
- 与实验性Pi API或线协议的向后兼容性。

## 16. 实施前需做出的决策

以下决策应在WP1/WP2/WP7开始前记录于本文件或小型ADR中：

1. 最终公共名称：`Plugin`与`Facet`、`Host`、`Peer`和`Connection`。  
2. 确切的中立上下文API及远程方法上下文位置。  
3. 上下文元数据传播是在首个RPC信封内，还是通过兼容的可选字段添加。  
4. 卸载期间已准入提供者调用的等待与取消策略。  
5. 对等协议协商与最大消息尺寸所有权。  
6. 状态序列间隙恢复：自动重新订阅与终端绑定失败。  
7. 打包器引擎及其运行时/开发依赖的放置。  
8. 清单模式、完整性算法与外部模块解析契约。  
9. 浏览器兼容核心行为是立即测试需求，还是仅限架构约束。

这些决策不应引入Pi概念到Chord。

## 17. 完成定义

当以下条件满足时，Chord的初始范围即为完成：

- 独立于Pi的单体应用可定义本地及远程单例/键值服务；  
- 两个对称对等方可相互通调、取消调用、订阅、断开连接及重水合；  
- 复制状态满足上述快照/更新及替换语义；  
- 插件从验证图激活并拥有所有注册资源；  
- 运行中的主机可加载、卸载、结构替换及保持形状一致重载插件生成；  
- 稳定的服务面即使提供者替换也能按指定存活；  
- Node打包器发出并重载内容寻址的独立插件条目；  
- 所有竞态与生命周期符合性测试通过；  
- 打包包可在Pi单体仓库外运行；以及  
- 自动化边界检查证明Chord无任何导入或依赖于Pi的其余部分。
