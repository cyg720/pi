重构当前`MemoryStorage`状态机为两阶段准备型变异：验证和分离产生一个候选对象，该对象可后续应用且不会失败。基于该对构建`MemoryStorage.commit()`，并复用同一状态机用于JSONL。JSONL必须追加每个准备好的侧边车记录，追加主标记，然后才应用准备好的内存变异。序列化或准备失败发生在文件I/O之前，不会毒化后端。保留索引/材料化对象保持分离于写入参数，读取永远不会暴露后端拥有的缓存对象。

JSONL创建使用`fsync?: boolean`，默认为`false`。使用`false`时，追加侧边车然后标记，无需显式刷新。使用`true`时，追加所有受影响的侧边车，刷新每个受影响的侧边车，然后追加主标记。不要显式刷新`main.jsonl`进行普通发布。仅主提交
没有侧车需要刷新。任何不确定的发布追加或刷新失败会毒化开放后端，并且不发布已准备好的内存突变。包 5 添加了单独的发布后刷新，以授权回收。

## 6–7. 跟踪器事务核心、定义和类型化访问

**前提条件：** `@earendil-works/chord/delta`导出符合规范的Astra-不可变优化版本`track`、`Tracker`、`Change`和`Prepared`，其草案放置拒绝不符合严格JSON格式的值。其他Delta目录下的实验版本不属于Pico API。

将这些包实现为一个里程碑。保持实现层分离，但不要构建临时的非类型化文档采集接口。实现这些测试所需的通用`Tx`表表面：精确表读取、分页会话/条目/任务扫描、`ReadAfterWrite`、ID创建写入和完整任务替换。扫描暴露存储游标和调用者选定的限制；它们永远不会隐藏无限全量扫描。会话、条目、任务和调度器的行为保持在包13–17中。
保持每个已加载文档一个Astra不可变跟踪器。其受信任的不可变`value`是当前可共享的修订版本。`prepare()`发出分离的自包含操作并使用优化的不可变应用器计算下一个修订版本；操作放置负载和该修订版本可能共享容器，且两者均不得被修改。`adopt()`验证所有权和修订版本，然后仅通过指针交换已计算的值。

实现作用域保持的单例/家族令牌和重载，用于Session、对话和任务所有者。仅`tx.doc()`是get-or-create：单例令牌提供`initial()`，而家族调用始终提供键和种子，且在缺少种子时仅使用第一个种子。定义是显式的类型参数，而非注册声明；冲突的定义声称持久化某种类型是调用方的误用。

首次访问`tx.doc()`时，通过逻辑地址缓存获取承诺，然后调用`tracker.beginChange()`。重复访问返回整个可能异步Session回调的相同覆盖草稿。Session行每个跟踪器仅允许一个打开的变更。回调以未解决的获取承诺结算时会拒绝：密封`Tx`，中止打开的变更，清空并中止待处理的获取，并观察其失败。回调失败会中止每个变更。回调成功则在将变更准备就绪后才允许Storage准入。

不要遍历已准备的操作负载或选定的基础，因为严格JSON格式由构造决定。跟踪器品牌和修订版本检查强制执行所有权和陈旧性。对每个已暂存的文档写入严格执行一次评估，并仅将选定的基础值或操作批次传递给Storage。通过Storage结算保持每个先前的不可变修订版本不变。成功后，通过指针交换采用每个准备好的值，并在释放行之前排队其不可变修订版本/操作的发布。Storage失败时，中止准备的变更，毒化Session，并发布任何内容。准备失败时按常规回滚；Package 8增加了检查点选择及其失败路径。

初始化器、迁移和替换根节点被复制到独占内核
所有权在严格的JSON检查后才成为可信的不可变修订版本。加载并分叉复制的根节点与存储分离，且无需另一份副本进行跟踪。Chord会复制并严格JSON检查每个草稿的放置位置，并在违规赋值时抛出异常。Astra空批次会抑制普通写入，而可回放的非空结构性无操作仍被视为有效写入和发布。无需运行时冻结或第二次操作负载复制。

查找快照、源和观察器时，若不存在则不会创建并返回`undefined`。`snapshot()`返回可共享的不可变当前修订版本；调用者必须在修改前复制。只读迁移可缓存其迁移的不可变跟踪器以及较旧的存储版本标记，无需写入；下一次成功的`tx.doc()`仍会写入所需的当前版本基础。事务阶段的创建或迁移只有在其包含的存储提交成功后，才会进入共享缓存。所有冷加载均在会话线上运行；加载的不可变修订版本可直接读取，无需复制。

测试回调失败；草稿撤销在回调结算时发生；并发重复获取；回调失败和成功时存在待获取项；密封后延迟获取；并发初始化一次；初始基础；家族种子优先；作用域/令牌不匹配；非创建性读取；共享不可变快照和稳定的历史修订版本；空批次抑制和可回放的冗余结构性无操作；多文档准备失败；不确定的存储失败中毒；通过存储结算保持旧修订版本的稳定性；指针交换和替代采纳；在可信的不可变契约下共享操作/修订负载；非JSON初始化器和草稿放置拒绝；赋值复制和重复放置独立性；权限和准备草稿不可逃逸；终端任务拒绝；由任务派生的对话身份；退休；重生绑定源；以及卸载/重载。将创建任务后文档、文档在终端拒绝后的处理、以及创建文档后终端结算合并为一个事务；内部候选验证不得触发`ReadAfterWrite`。

## 19. 结构化并发

实现规范 §5.5 及其后果，替换`after`和`pi.post-tools`。
- 所有权：需要 `TaskOptions.ownership`（`{ kind: "conversation" }` 或 `{ kind: "task", taskId }`）；`TaskRecord.owner?: TaskId`；子任务存在于其所有者的对话中；`background` 仅适用于对话拥有的任务；新任务或对话所有权需要一个存活的所有者（不是 `completing` 或 `terminal`）。更新每个 `createTask` 调用站点，包括工具的 `api.createTask`、示例和测试。存储：持久化 `owner` 和新的状态（内存、JSONL、SQLite 模式就地编辑；未完成期间不进行迁移），符合性用例。无所有者索引：调度器从加载的存活任务中推导边。
- 状态：在 `TaskState` 和每个后端及状态扫描中记录真实的 `waiting { checkpoint, on, policy }` 和 `completing { outcome }` 状态；`NextTaskState` 获得 `waiting`；`runtime.outcomes()`；`inspect()` 报告 `completing`。移除 `after`（记录、选项、调度器依赖处理）。
- 调度器：等待任务永远不会被预留，直到 `on` 中的每个任务都

会话任务图的实时可观察视图，用于UI和调试，例如`ConversationView`的对话视图：每个活跃任务及其所有者边（对话或任务）、状态（`running`，`waiting on …`，`completing`）、背景标志和所拥有的对话，每次提交后作为复制状态或监视发布。`inspect()`已提供一次性的实时任务记录快照。在最终符合包之后指定并构建它。

在`spec.md` §9.5中规定：`Harness.taskGraph()`和`watchTaskGraph()`挂载每个以ID为键的活跃任务及其提交状态（阶段、等待、持有结果状态）、所有者边、标志和所拥有的对话。派生状态（`blocked`，`ready`，`on`的实时部分）保留在`inspect()`。实现于`src/harness/task-graph.ts`，测试于`harness-task-graph.test.ts`和生命周期测试，示例见24。
